## [Unreleased]

### Added
- **Run-log pipeline manifest** — `pipeline_start` gains a nested `manifest` object describing the run's *definition* for a dashboard's read-only Overview, additive to run-log schema v1 (`SCHEMA_VERSION` stays 1). It is introspected once at run start from the real `Pipeline` / `Step` / response-model objects — row-independent, deterministic, and never touching the cached `system` prompt half (#107). Carries `accrue_version`; a `config` block mirroring the run's `EnrichmentConfig` (`max_workers`, `caching`, `checkpointing`, `batch`, `capture`); a `steps` array (`type` = `type(step).__name__`, per-step `model` with `id`/`provider`/effective `temperature`+`max_tokens` — `null` for FunctionSteps — plus `produces` / `depends_on` / `condition`); and a `fields` array (the enrichment-field schema: `type` — `str`/`int`/`float`/`bool`/`enum`/`list`/`json`/`unknown` — with enum members, description, producing `step`, and an `internal` flag for `__`-prefixed inter-step fields). Field types come from inline `FieldSpec`s or a custom Pydantic `schema=`; sources that can't be introspected cheaply report `type:"unknown"` rather than a fabricated value. `JsonlRunLogger` accepts a `config=` argument to feed the block. `tests/fixtures/run_small.jsonl` now includes the manifest and still regenerates byte-stably. See `docs/guides/run-log.md`. (#138)
- **Run-log v0.2: `RowAttemptEvent` + capture tiers + prompt sidecar** — the serialized contract the dashboard's attempt inspector reads, all additive to run-log schema v1. A new `RowAttemptEvent` lifecycle hook (`on_row_attempt`) fires once per LLM provider attempt inside both of `LLMStep.run()`'s retry loops — `kind="api"` when the call raised, `kind="parse"` when it returned and was parsed — carrying `attempt`, `status`, `latency_ms`, `backoff_s`, and `error`; it projects to an additive `row_attempt` run-log record, so a cell that retries emits several `row_attempt` lines then one `row_complete`. `run(..., capture="metadata"|"prompts"|"full")` (default `"metadata"`) sets how much lands on disk: `"metadata"` writes attempt metadata only (row bodies are often PII), `"prompts"` also persists each attempt's rendered system/user messages and response to a `<run>.prompts.jsonl` sidecar — append-only, `0600`, never inlined — referenced from `row_attempt` by a `prompt_ref` `{off, len}` byte span; `"full"` behaves as `"prompts"` today (provider adapters expose no cheap raw payloads). Captured bodies pass through the same `_sanitize_secrets` redaction as error text. New exports: `RowAttemptEvent` and `read_prompt_ref(sidecar, off, len)`. Golden fixture at `tests/fixtures/run_captured.jsonl` (+ its `.prompts.jsonl`); the existing `run_small.jsonl` is unchanged. See `docs/guides/run-log.md`. (#134)
- **`Pipeline.retry_failed()` / `retry_failed_async()`** — re-run only the cells a previous run left failing. The checkpoint now records which row indices errored in each completed step, and `CheckpointManager.resume_failed()` selects those `(step, row)` cells on top of `load()`'s existing strict validation. Everything that succeeded is served from the checkpoint and never re-invoked, so healing 5 failures in a 10,000-row run costs 5 calls; `rows=` / `steps=` narrow the retry further, and failures left out stay recorded for a later attempt. Pointed at the failed run's `run_log`, the retry appends to it under the same `run_id`, framed by additive `retry_start` / `retry_end` records (schema v1) so recovered cells arrive as ordinary `row_complete` lines a dashboard can apply directly. This is the API behind a "retry failed rows" button, and the groundwork for CLI resume. See `docs/guides/caching.md`. (#129)
- **Run log (contract v1)** — `run(..., run_log=True)` streams the run as an append-only, per-line-flushed JSONL file (`.accrue/runs/<run_id>.jsonl`, or pass a path): `pipeline_start` / `step_start` / `row_complete` / `step_end` / `pipeline_end` records with status, errors, per-row values, and token usage. `JsonlRunLogger` is exported for standalone use with `hooks=logger.hooks`; user hooks are merged, not replaced. `RowCompleteEvent` gains additive `usage` and `elapsed_ms` fields, and `StepStartEvent.execution_mode` / `StepEndEvent.execution_mode` / `StepEndEvent.batch_id` are now actually populated at the fire sites. Contract spec in `docs/guides/run-log.md`; golden fixture for consumers at `tests/fixtures/run_small.jsonl`. (#128)
- **`accrue.compare(result_a, result_b)`** — diff two pipeline runs. Aligns rows explicitly (positionally for default `RangeIndex`, by label for real indexes, with a warning and positional fallback on non-unique or mixed-kind indexes) rather than via a blind index intersection that silently yields garbage. `changed_rows(field=None)` returns a before/after frame of differing rows; `distribution_shift()` reports per-field churn — frequency tables for enums, mean/std for numbers, differs-count plus an approximate token delta otherwise. Cell equality is null-safe and container-safe. (#36)
- **`Pipeline.plan(data, sample_size=3)`** — dry-run preview returning a `PipelinePlan`. Introspects each step's resolved system prompt and JSON schema, runs a capped real sample, and extrapolates measured token usage to the full dataset; `summary()` renders a terraform-plan-style preview. Cost is extrapolated only over rows that actually called the API, so cached sample rows don't deflate the estimate. Also adds `run(..., confirm=True)` to print the plan and prompt before the full run. See `docs/guides/plan-mode.md`. (#12)
- **`output_file` / `PipelineResult.save(path)`** — write enriched data to disk, inferring format from the extension (`.csv` / `.json` / `.parquet`). When `output_file` is passed to `run()` / `run_async()`, the save happens *before* the call returns, so an error in the caller's own post-processing can no longer discard a completed, already-paid-for run. (#10)
- **`PipelineResult.report(format, path, disable)`** — heuristic-driven Markdown/HTML run summary. Headlines suspicious patterns (enum collapse, numeric clipping, length anomalies, retry storms, refusal phrases, cache thrash, cost outliers) with a probable cause and a suggested action; backed by a per-step stats table. Pass `disable=[...]` to mute individual heuristic codes. See `docs/guides/report.md`. (#32)
- `PipelineResult` now exposes `pipeline_elapsed_seconds`, `step_elapsed_seconds`, and `field_specs`, populated by `Pipeline.run_async()` so reporters and custom heuristics can introspect.

### Changed
- **Checkpoints are now keyed to the data's *content*, not just its shape.** `derive_data_identifier()` hashed only `{columns, num_rows}`, while `checkpoint_dir` defaults to a single global XDG state directory — so two unrelated datasets with the same columns and row count resolved to the *same* checkpoint file, and the second silently received the first one's enrichments with no error anywhere. The identifier now folds in a sha256 digest of the first and last five rows' values (stable across processes, and defined for `list[dict]` rows with heterogeneous keys). The intended consequence: **editing the data invalidates the checkpoint** and the next run starts fresh. Pass an explicit `data_identifier=` when you need one to survive edits. Existing checkpoint files, written under the old identifier, are not found by the new one.
- **A retry now re-runs the downstream cells of every cell it heals** — a semantic change to `retry_failed()` and to checkpoint auto-resume. Previously, healing `score` for row 7 left the `flag` step's row 7 holding the answer it had computed from the `None` placeholder the failure left behind: stale wrong data, an empty `errors` list, and `session.finish()` then deleted the checkpoint that was the only record of it. Dependents are walked transitively through the DAG and re-run **only for the healed rows**; sibling branches that consumed nothing broken are untouched. A retry therefore costs the failed cells plus their dependents for those rows — still nothing for the rows that worked. `retry_start.cells` in the run log now reports that resolved set, so a dashboard marks exactly the cells that will change.
- **Run ids are UTC-based and unique.** `new_run_id()` returned a whole-second *local* timestamp, so two runs started in the same second shared one id — and, under `run_log=True`, one file — while the id disagreed with the UTC `started_at` recorded beside it. It is now `YYYY-MM-DD-HHMMSS-xxxxxx` (UTC plus a short random suffix); treat it as opaque.
- **`Pipeline.execute()`'s `on_step_complete` callback takes a fourth argument**, the set of row indices the step skipped via `run_if` / `skip_if`. Internal API; callers using `Pipeline.run()` / `run_async()` / `Pipeline.runner()` are unaffected.
- **A checkpointed row that *errored* now re-runs on resume.** Previously "step completed" meant every one of its rows was done, so a resumed run silently kept the `None` placeholder a failed row had been given, and only a full re-run (paying for every row again) could recover it. Checkpointed now means done only for cells that actually succeeded. A run that ends with row errors also keeps its checkpoint instead of deleting it — that record is what a resume, or `retry_failed()`, reads. Clean runs still clean up on success. (#129)
- **`Pipeline.run()` / `run_async()` honour `enable_checkpointing`.** The flag was documented as working on `run()` but only ever took effect through `pipeline.runner(config)`; on `run()` it was silently a no-op. Both entry points now write and resume from the same checkpoint file for the same dataset, so a run started with one can be resumed or retried with the other. `Pipeline.plan()` forces checkpointing off for its capped sample, so a dry run can never write or resume the real run's checkpoint. (#129)
- **`Pipeline.execute()` returns a 4-tuple** `(accumulated, errors, cost, step_elapsed_seconds)` instead of a 3-tuple. Internal API (not exported in `accrue.__all__`); callers using `Pipeline.run()` / `run_async()` are unaffected.
- **`Pipeline.execute()`'s `on_step_complete` callback takes a third argument**, the step's `list[RowError]`, and gains a `retry_cells` keyword. Internal API; callers using `Pipeline.run()` / `run_async()` / `Pipeline.runner()` are unaffected. (#129)

### Removed
- **The `accrue[ui]` extra.** accrue-ui is not on PyPI and PyPI rejects direct git URLs in dependency specs, so `pip install 'accrue[ui]'` could only ever resolve to a package that does not exist — and it was the lead instruction in both the `accrue watch` hint and the README. Install accrue-ui from the repo instead: `pip install git+https://github.com/matt-house-e/accrue-ui`. The extra is commented out in `pyproject.toml`, ready to restore once accrue-ui is published.

### Fixed
- **A checkpoint write can no longer take the run down with it.** A step value JSON cannot encode (`UUID`, `Path`, `Enum`, …) made `save_step()` raise straight through `Pipeline.execute()`, killing the run *after* the API spend and discarding every result. The write is now guarded: it logs an error, degrades to running without checkpointing, and the run completes. Partial (intra-step) checkpoint writes are guarded the same way.
- **Run logs no longer leak secrets or default to world-readable.** Error messages now pass through the same `_sanitize_secrets` redaction the checkpoint path has always applied — a provider error can quote request headers, and the log outlives the process — and the file is created (and chmod'd) `0600` instead of inheriting the `0644` umask default. `_SECRET_PATTERNS` also learned Google AI Studio / Gemini keys (`AIza…`).
- **Run logs are strict JSON again.** A `NaN` or `±inf` in a step's values was written as a bare `NaN` / `Infinity` literal, which no strict parser accepts. Non-finite floats are now recursively replaced with `null` and every record is dumped with `allow_nan=False`.
- **A `row_complete` is never silently dropped.** A value with non-string dict keys, or a reference cycle, raised inside the logger — and because hook errors are swallowed by design, the line simply vanished, breaking the documented "every row of every executed step gets exactly one `row_complete`" guarantee. Such a record is now re-emitted with its values replaced by `{"__unserializable__": true}`.
- **Appending to an existing run log keeps `t` non-decreasing.** Pointing `run_log=` at a file that already has records restarted the clock at zero. The file's last `t` is now applied as an offset on every append, not only on a retry.
- **Concurrent checkpoint writers no longer corrupt the atomic write.** The temp file was named `<checkpoint>.json.tmp` — one constant name per path — so two processes checkpointing the same dataset wrote the same temp file and `os.replace()`d a half-written mixture into place. The name now carries the pid and a random suffix.
- **`retry_failed(steps=...)` validates the step names.** A typo selected nothing, re-ran nothing, and reported a clean run; it now raises `PipelineError` naming the unknown steps.
- **A retried cell that gets *skipped* stays failed.** If a `run_if` / `skip_if` predicate now excludes a cell being retried, nothing ran — so the recorded failure is kept instead of being erased along with the checkpoint.
- **A partial checkpoint mid-retry no longer demotes the step.** A retried step's results are seeded from the checkpoint, so a partial save now keeps its completed status and writes its row errors through. Previously the crash-recovery path marked it "never ran", and the next retry re-executed the whole step at full price instead of the handful of cells still failing. A step running for the first time is still marked unfinished, as before.
- Persisted row-error messages are capped at 500 characters — a provider can return a multi-megabyte body, and the full exception is still in `result.errors`.
- `accrue watch` distinguishes "accrue-ui is not installed" from "accrue-ui is installed but raised on import", so a broken dependency inside accrue-ui no longer sends you to reinstall it, and it propagates a delegate's exit code only when the delegate actually returned an `int` (`or 0` mapped any falsy return to success).
- A retry no longer invents a `display_key` when the run it is appending to recorded `null`, which had keyed the retry's rows differently from the rows above them in the same file.
- Docs: `JsonlRunLogger`'s `data` / `segment` / `t_offset` / `retry_cells` arguments are documented in `docs/reference/api.md`, and `docs/guides/run-log.md` notes that an auto-resumed run produces a partial-coverage log (steps served from the checkpoint emit no records).
- **`batch=True` no longer crashes mid-run against an OpenAI-compatible gateway.** `LLMStep.is_batch_eligible` gated the batch path on `isinstance(client, BatchCapableLLMClient)`, but that Protocol is `runtime_checkable`, so the check only confirmed the three batch methods *exist*. `OpenAIClient` defines them unconditionally — including when a `base_url` points at OpenRouter, Groq, Together, vLLM, or Ollama, none of which serve the Batch API. Any such step reported itself eligible and then died inside `client.files.create()`, after earlier steps in the pipeline had already been paid for. Batch capability is now resolved by `is_batch_capable(client)`, which combines the structural check with an optional `supports_batch` property; `OpenAIClient.supports_batch` is `False` whenever `base_url` is set. Such steps degrade to realtime execution and warn once that they are paying non-batch prices, matching the documented fallback for non-batch-capable clients. Calling `submit_batch()` / `poll_batch()` on a `base_url` client directly now raises a `StepError` naming `batch=False` as the fix, instead of a 404 from the gateway. Custom adapters that omit `supports_batch` are still treated as capable, so no existing client changes behaviour. `is_batch_capable` is exported from `accrue`.
- **The Claude 5 family works again.** The Anthropic adapter always sent `temperature` and no code path could omit it — `llm.py` substituted a literal `0.2` when none was given, and `EnrichmentConfig.temperature` itself defaults to `0.2`, so `None` never reached the adapter. Claude 5 models reject an explicit temperature, so every call to `claude-sonnet-5`, `claude-opus-5`, or `claude-fable-5` returned a 400 with an error that named the model rather than accrue. The parameter is now omitted for models that reject it (matched by family, so unreleased Claude 5 variants and `anthropic.` / `us.anthropic.` prefixes are covered), on both the realtime and batch paths. Dropping an explicit value warns once, and temperature-related API errors carry an actionable hint. Also covers `claude-opus-4-7` and `claude-opus-4-8`, which removed the sampling parameters too. (#109)
- **Prompt caching now actually hits.** The row's own data was built into the same system message the Anthropic adapter marks `cache_control: {"type": "ephemeral"}`, so the cached prefix changed on every row: every call wrote a fresh entry at 1.25x input and none was ever read at 0.1x — a standing ~25% surcharge on every input token for a feature that never fired. The prompt builder now returns the prompt already split (`build_prompt() -> PromptParts(system, user)`): instructions and `<field_specifications>` stay in the cacheable system block, `<row_data>` and `<prior_results>` move to the user message. The reminder stays last in the user message, preserving the sandwich pattern. (#107)
- Anthropic: `cache_creation_input_tokens` and `cache_read_input_tokens` are now carried through `UsageInfo`, `StepUsage`, and `CostSummary`, and counted in `total_tokens`. Cost reports previously omitted prompt-cache tokens, under-reporting the bill by up to ~63x on cached workloads. The pipeline summary now shows cache write/read totals so silent prompt-cache failures are visible. (#108)

### Internal
- CI: Markdown is excluded from ruff (`extend-exclude = ["*.md"]`). The dev extras are unbounded, so CI resolved ruff 0.16, which began formatting Python code blocks inside Markdown and failed `ruff format --check` on 24 untouched files across `README.md`, `docs/`, and `.claude/skills/`. The network-blocking test fixture also now patches `httpx2` as well as `httpx`, since `openai>=3` moved to the `httpx2` package and CI installs only `.[dev]`, which pulls neither on its own. `main` had been red since both landed. (#113)
- CI: `test.yml` now also runs weekly on a schedule. Because the dev extras are deliberately unbounded, an upstream release can break `main` with no commit landing here — which is exactly what happened twice in 2026, leaving `main` red for six weeks because nothing triggered a build. A scheduled run against a fresh dependency resolution catches that class of breakage in days, with no LLM involved.
- The scheduled maintenance workflow was rewritten and moved to `maintenance.yml`, monthly. It now posts only when it finds something (the old prompt explicitly required posting even when clean, which produced ten near-identical issues), maintains one rolling issue instead of a dated one per run, sweeps every exported symbol for doc drift rather than three at random, and can see CI and PR state — the previous tool allowlist excluded `gh run` and `gh pr`, so it was structurally unable to notice the outage above. Version coherence and CHANGELOG-section checks moved out of the LLM sweep into `tests/test_repo_metadata.py`, where they run on every commit.

## [1.3.0] - 2026-05-19

### Added
- Agentic SDLC scaffolding: GitHub Actions for `@claude` mention, PR review, weekly maintenance, and dogfooded issue triage. Repo-scoped slash commands under `.claude/commands/`. Local `PostToolUse` hook for ruff-on-edit. See `AGENTS.md`.

### Changed
- **`EnrichmentConfig.enable_caching` now defaults to `True`** (was `False`). Re-runs of unchanged inputs no longer re-pay the API cost. Opt out with `EnrichmentConfig(enable_caching=False)` for one-off runs.
- **`LLMStep` auto-detects provider from model name.** `claude-*` → `AnthropicClient`, `gemini-*` → `GoogleClient`, anything else (or any model with `base_url` set) → `OpenAIClient`. Previously every Claude/Gemini user had to pass `client=AnthropicClient()` or `client=GoogleClient()` explicitly. Explicit `client=` still wins. (#23)

### Fixed
- `LLMStep.parse_response` now strips markdown code fences before `json.loads`. Fixes parse failures with Claude Haiku + grounding tools, where the structured-output constraint is disabled and the model wraps JSON in ` ``` ` fences. (#7)
- `accrue/__init__.py` `__version__` was out of sync with `pyproject.toml`.
- Google provider: Option-B rate-limit fallback now uses a word-boundary regex (`\brate[\s_-]?limit\b`) instead of bare `"rate" in exc_str`, preventing false positives on words like "iterate" or "accelerator". (#80)
- Google provider: `DeadlineExceeded` errors now set `status_code=408` (both typed Option-A and substring Option-B paths) for consistency with the Anthropic adapter. (#80)
- Checkpoint: pre-1.2.1 files using the legacy `__type__` sentinel are now detected, logged as a `WARNING`, and discarded so pipelines resume cleanly instead of silently misreading typed values. (#80)
- Pipeline: submit-batch cleanup now logs a `WARNING` for any `cancel_batch` failures so users know if orphaned batches may still be billable after a submit error. (#80)

### Performance
- **Streaming worker pool** replaces eager `asyncio.Task` materialization in the realtime pipeline path. Previously, running a step across N rows created N pending tasks up-front; for 50k rows × multi-step pipelines that meant hundreds of thousands of objects in the event-loop's ready queue. The new design keeps a fixed pool of `max_workers` tasks pulling from a bounded `asyncio.Queue`, so memory and scheduling overhead is O(max_workers) regardless of row count. All existing semantics are preserved: `on_error="raise"/"continue"`, hooks, caching, `run_if`/`skip_if` predicates, checkpointing, and cancellation drain. (#78)

### Internal
- `AnthropicClient._warned_grounding_schema` is per-client-instance scope (not per-process). `LLMStep` constructs a fresh client per `Pipeline.run_async()` call, so the grounding-schema incompatibility warning fires once per run. (#80)
